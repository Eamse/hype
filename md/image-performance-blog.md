# 웨딩 사진 사이트 이미지 로딩 성능 개선기

## 문제: 사진 많은 페이지가 배포 여부와 무관하게 심하게 느림

Next.js + Cloudflare R2로 이미지를 서빙하는 웨딩 사진 플랫폼에서, `/products`, `/packages`처럼 사진이 많은 페이지에서 첫 방문 시 10~50초씩 로딩이 걸리는 문제가 발생했다. 특히 여러 썸네일이 동시에 로드되는 화면에서 심했다.

## 원인 분석

1. **업로드 압축 화질이 지나치게 높았음**: 원래 웨딩 사진 화질 유지를 위해 3840px / webp quality 92로 저장하고 있었는데, 이 큰 원본을 `next/image` 옵티마이저가 매 요청마다 화면에 필요한 작은 크기(64px~)로 실시간 리사이즈하고 있었음. 이 연산 자체가 약한 VPS(1.9GB RAM)에 부담을 줌.
2. **배포마다 이미지 캐시가 초기화됨**: `next.config.ts`의 `output: 'standalone'`이 매 빌드마다 `.next/standalone`을 완전히 새로 생성하는데, 배포 스크립트가 런타임에 쌓인 리사이즈 캐시(`.next/standalone/.next/cache/images`)를 다음 빌드로 넘겨주지 않고 있었음. 배포할 때마다 콜드 캐시를 반복.
3. **큰 원본과 작은 썸네일이 같은 파일을 공유**: 상세 갤러리에서 64px 썸네일 스트립과 확대 뷰어가 같은 원본 파일(1600~3840px)을 가리키고 있어서, 썸네일 표시할 때마다 서버가 그 큰 파일을 실시간으로 축소해야 했음.
4. **캐시 워밍 스크립트가 다루는 폭(width)이 실제 요청 폭과 안 맞음**: `next/image`는 `sizes` 힌트에 따라 `deviceSizes`(640~3840px) 또는 `imageSizes`(16~384px) 중 하나를 선택하는데, 64px 썸네일처럼 고정 크기를 지정한 경우 후자를 쓴다. 캐시 워밍 스크립트는 전자만 데워놔서, 상세 갤러리 썸네일은 항상 콜드 상태였음.
5. **R2 기본 도메인이 프로덕션 부적합**: `pub-xxxx.r2.dev` 도메인은 Cloudflare가 공식적으로 "테스트/개발용, 프로덕션 사용 비권장"이라 명시한 도메인. 해외(필리핀)에서 실제로 이미지가 깨지는 현상 확인.

## 해결 과정

**1단계 — 업로드 압축 기본값 하향 + 캐시 인프라 정비**
- 기본 압축을 3840px/q92 → 1920px/q78로 낮추고, 화면을 꽉 채우는 히어로 이미지만 예외로 3840px/q90 유지
- Cloudflare Cache Rule로 `/_next/image*` 엣지 캐시를 30일 강제 유지
- `next.config.ts`의 `minimumCacheTTL`을 1년으로 연장
- 배포 스크립트(`deploy.sh`, GitHub Actions)에 이미지 리사이즈 캐시 백업→복원 로직 추가해 "배포마다 캐시 초기화" 문제 해결
- 기존 이미지 일괄 재압축 마이그레이션 스크립트 작성 및 실행: **683건 성공 / 3건 실패**

**2단계 — 용도별 실제 작은 파일 사전 생성 (썸네일 폴더 분리)**
- 카드 그리드용 썸네일은 업로드 시점에 아예 640px/q75로 별도 저장(`THUMBNAIL_RESIZE_WIDTH/QUALITY` 추가)하도록 업로드 API 수정
- 기존 카드 썸네일 재압축 마이그레이션: Package 17건 처리, **42.7MB 절약**
- 상세 갤러리도 동일 문제(큰 원본을 썸네일로 재사용) 확인 → `ProductImage`/`PackageImage`에 `thumbUrl` 컬럼 추가, 업로드/드라이브 동기화 시 640px 전용 파일 별도 생성
- 기존 갤러리 사진 백필: **PackageImage 1,251건** 처리

**3단계 — 캐시 워밍 스크립트 정비**
- `deviceSizes`(640~3840px) 8개 폭을 전부 데우도록 확장
- 요청 타임아웃(30s) 추가 — 응답 없는 요청 하나가 전체 워밍을 무한정 멈추던 버그 수정
- 최종 실행 결과: **2,742건 성공 / 2건 실패**

**4단계 — 갤러리 메인 뷰어 연산 자체 제거**
- 상세 갤러리 확대 이미지는 업로드 시점에 이미 웹용으로 압축돼있으므로, `next/image`의 `unoptimized` 옵션으로 리사이즈 연산 자체를 건너뛰고 R2 파일을 직접 서빙하도록 변경

**5단계 — R2 커스텀 도메인 마이그레이션**
- `pub-xxxx.r2.dev`(테스트용) → `photo.hypewedding.kr`(정식 서브도메인, Cloudflare 정식 프록시)로 전환
- 기존 이미지 URL 일괄 마이그레이션: **1,287건** 호스트 치환
- 이후 갤러리 메인 뷰어에 `unoptimized` 재적용 — 이번엔 안정적인 도메인이라 해외에서도 문제없이 서빙됨

## 결과

- 최초 발생했던 10~50초 대기 현상 완전히 사라짐
- 배포할 때마다 캐시가 초기화되던 근본 원인 해결로, 배포 직후에도 성능 저하 없음
- 해외(필리핀)에서도 이미지 정상 로딩 확인
- 상세 갤러리 썸네일 스트립 + 확대 뷰어 둘 다 체감 속도 개선 확인

## 성능 지표 (실측)

| 항목 | 이전 | 이후 |
|---|---|---|
| 콜드 캐시 응답 시간 (썸네일, w=640) | 10~50초 | 0.47초 |
| 워밍된 캐시 응답 시간 | - | 0.43~0.46초 (`cf-cache-status: HIT`) |
| 패키지 카드 썸네일 재압축 절약 용량 | - | 42.7MB (17건 기준) |
| 재압축 마이그레이션 처리 건수 | - | 683건 (기존 전체 이미지) |
| 캐시 워밍 처리 건수 | - | 2,742건 |
| 갤러리 썸네일 백필 건수 | - | 1,251건 (PackageImage) |
| URL 도메인 마이그레이션 건수 | - | 1,287건 |

## 배운 점

- 캐시 워밍은 "확률을 낮추는 완화책"이지 완벽한 해결책이 아니다 — 브라우저/디바이스/폭 조합이 무한히 많아서 100% 커버는 불가능. 근본 원인(연산 자체를 없애는 것)을 먼저 해결하는 게 맞는 방향이었다.
- "이미 압축된 파일이 저장소에 있다"와 "그 파일이 그대로 서빙된다"는 다른 얘기다 — 우리 경우 `next/image` 옵티마이저를 한 번 더 거치고 있어서, 저장 시점 압축과 서빙 시점 최적화를 분리해서 생각해야 했다.
- 인프라 도구(R2, CDN)의 "테스트용" vs "프로덕션용" 구분을 처음부터 확인했어야 했다.

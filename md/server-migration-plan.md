# 자체 서버 전환 계획

## 배경

- 원래 iwinv VPS에 자체 호스팅(Next.js + 로컬 Postgres)으로 운영하다가, 크립토마이너(XMRig 계열) 침해 사고 발생 → 서버 삭제
- 이후 "클라이언트한테 진행 상황 빨리 보여주기용"으로 Vercel + Neon(서버리스 Postgres)에 임시로 옮겨서 지금까지 운영 중
- Vercel/Neon은 편의상 선택한 것일 뿐, 계속 거기 있어야 할 필수 이유는 없음

## 목적

**내 서버를 직접 운영해보는 학습 경험.** 비용 절감이 주목적이 아니라, 서버 운영 자체를 배우고 싶은 게 핵심 동기.

## 방향

- **앱 서버 + DB(Postgres) 둘 다 자체 서버로 이전** (Neon에 남겨둘 필수 이유 없음, 예전 iwinv 구조로 회귀)
- 단, **기존 프로덕션(Vercel+Neon)을 먼저 내리지 않고**, 새 서버를 별도로 세팅 → 충분히 검증 후 도메인 전환하는 순서로 진행 (전환 중 서비스 중단/재사고 리스크 최소화)

## 진행 순서

1. **서버 구매**
   - DB까지 같은 서버에서 돌릴 거라 여유 있게: iwinv `vgna_4_n` (4vCPU/4GB) 권장
   - (참고: 앱만 돌릴 거면 `vgna_2_n` 2GB로도 충분했지만, DB까지 얹으면 메모리 여유 필요)

2. **보안 하드닝 — 서버 켜자마자 바로 세팅 (미루지 말 것, 지난번 사고 원인)**
   - `ufw` 방화벽: SSH, 80/443 포트만 개방
   - `fail2ban`: 무차별 로그인 시도 차단
   - SSH 비밀번호 로그인 금지 → 키 인증만 허용
   - `root` 직접 로그인 금지
   - SSH 포트를 22 대신 다른 포트로 변경 (스캔봇 회피)

   > **지난번 사고 원인 (확인됨):** 서버 최초 부팅 시 방화벽 미설정 + 비밀번호 SSH 인증이 켜진 상태로 약 10분간 인터넷에 노출됐고, 그 사이 자동 스캐닝 봇에 브루트포스로 침투당해 크립토마이너가 심어짐. SSH 키 인증 전환은 그 이후에 이뤄져서 이미 늦은 상황이었음 — 즉 키 인증 자체가 뚫린 게 아니라, **키 인증으로 전환하기 전의 짧은 노출 창(window)이 문제**였음. 그래서 이번엔 방화벽·키 인증을 서버가 인터넷에 노출되기 전에 미리 다 준비해두고 켜야 함(순서 절대 바꾸지 말 것).

3. **Postgres 자체 설치 및 보안**
   - `apt install postgresql`
   - **외부 노출 금지** — `localhost`에서만 접속되도록 바인딩 (앱이 같은 서버에서 도니까 로컬 연결로 충분)
   - DB 백업 자동화를 처음부터 세팅 — `pg_dump` cron으로 매일 덤프 떠서 R2 같은 외부 스토리지에 업로드 (실 서비스 데이터가 있으므로 이번엔 필수)

4. **GitHub Actions로 배포 자동화**
   - 새 SSH 배포 키 발급 (기존 iwinv 서버가 삭제되면서 예전 배포 키는 이미 무효)
   - CI/CD 파이프라인 재설정

5. **충분히 안정성 검증 후 도메인 전환**
   - 이미 구매/DNS 설정해둔 도메인을 새 서버로 최종 연결

6. **(추후, 여유 생기면) 성능 테스트·모니터링 스택 구축 — k6 + Prometheus + Grafana**
   - 지금까지는 k6 단독으로 부하 테스트 후 터미널에 결과(p95, req/s 등) 텍스트로만 확인
   - Prometheus(지표 수집·저장) + Grafana(실시간 그래프 시각화)를 붙이면, 테스트 도중 "부하가 늘어날수록 응답시간이 어느 시점부터 튀는지"를 실시간 그래프로 확인 가능
   - 흐름: `k6 (부하 발생) → Prometheus (지표 수집·저장) → Grafana (실시간 대시보드)`
   - 실무 표준 조합이라 포트폴리오/면접에서도 "모니터링 대시보드 구축 경험"으로 어필하기 좋음
   - 로컬에서 Docker로 Prometheus+Grafana 띄우고 k6 결과를 흘려보내는 것부터 시작 가능 (서버 인프라 자체와는 별개로 먼저 로컬 연습 가능)

---
name: 협업 방식 - 코드를 먼저 짜지 말 것
description: 무작정 코드 작성 금지, 함께 짜기. 급할 때만 직접 작성 요청. 코드 설명 방식도 포함.
type: feedback
---

코드를 먼저 짜주지 말고 같이 짜야 한다. 급하거나 사용자가 명시적으로 요청할 때만 직접 작성.

**Why:** 사용자가 비즈니스 로직 훈련 중이며 코드 짜는 법을 배우고 싶어서. 운영 경력 6년 후 개발로 전향한 케이스라 하나하나 다 알고 가는 걸 선호함.

**How to apply:** 코드 설명 시 아래 방식으로 디테일하게 설명할 것:

- 함수/메서드가 뭔지 (어디서 온 건지, import 필요한지 등)
- 내장 함수면 어떤 기능을 하는 함수인지
- 각 인자가 뭘 의미하는지
- 다른 값을 넣으면 어떻게 되는지
- 실제 데이터 예시로 설명

예시: `process.exit(1)` 설명 시

- process가 뭔지 (Node.js 전역 객체, import 불필요)
- exit()이 뭘 하는지 (프로세스 강제 종료)
- (1)이 뭔지 (종료 코드, 0=정상, 1=비정상)
- 2를 넣으면 어떻게 되는지 (커스텀 에러 코드 가능하나 관례상 1 사용)

**왜 이렇게 짜는지:**
문법 설명하면서 "왜 이 방식을 선택하는지" (예: 왜 try-catch를 여기 쓰는지, 왜 이 위치에 미들웨어를 넣는지)
매서드에 대한 설명도 해줄 것, 왜 이 매서드를 사용했는지 이 매서드는 어떤 용도이고 어떻게 사용하는지

**기존 코드 패턴 따라가기 명시:**
새 기능 짤 때 프로젝트에 이미 있는 비슷한 패턴 먼저 찾아보고 그거 참고하라는 룰 — 일관성 있는 코드 베이스 만드는 습관.

**에러 메시지 읽는 법 우선 시도**
에러 나면 바로 답 주지 말고, 에러 메시지 읽고 어디서 났는지 먼저 찾아보게 유도 — 디버깅 근육 키우는 거.

**코드 리뷰 관점 추가**
완성된 코드 보고 "이 코드 면접에서 설명할 수 있는지" 자가 체크하는 습관 — 지금 하고 있는 것처럼.
